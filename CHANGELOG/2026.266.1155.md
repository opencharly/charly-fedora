# 2026.266.1155 — feat: add the check-fedora-repo R10 bed for the published package repo

## Summary of changes

Relocate the `check-fedora-repo` R10 check bed (and the `fedora-repo-vm` template it deploys) from `opencharly/charly`'s `charly.yml` into this repo, which OWNS the artifact the bed tests. A check bed must live in the repo that owns what it tests: the check-bed runner's dev-tree override (`proc.SelfSuperprojectOverridePair`, `spec/proc/repo_override.go`) points the bed PROJECT's own superproject's `@github` refs at the local tree, so a candy owned by another repo was never exercised as in-development code while its bed sat in `charly`.

**Changed files:**

- `charly.yml` (ADDED, 103 lines) — the project definition for this repo: top-level `version: 2026.249.2125` + `repo: github.com/opencharly/charly-fedora`, `defaults` (amd64, `ghcr.io/opencharly`, `build: [rpm]`, no auto-merge), the `fedora-repo-vm` disposable Fedora Cloud 43 VM template (`kind: cloud_image`, libvirt, bios, generated SSH key, `sudo` via cloud-init), and the `check-fedora-repo` bed (`from: fedora-repo-vm`, `disposable: true`) whose 4 runtime steps assert: `fedora-repo-added`, `fedora-charly-installed`, `fedora-charly-version` (installed `/usr/bin/charly version` == the CalVer the rpm recorded), `fedora-welded-command-project-less` (welded command plugins dispatch from `/tmp`).
- `.gitignore` (ADDED, 16 lines) — the standard generated-artifact rules for a charly project: `.build/`, `.containerignore`/`.dockerignore`, `.check/`, `output/`, editor scratch (`*.swp`, `*~`), and migration rollback backups (`*.bak`, `*.bak.*`). This is a new file in this repo (it previously had none), not an append below existing entries.

No `.github/workflows/` file is changed by this PR (the repo's existing `build.yml` / `tag-on-merge.yml` are untouched).

**Reconciliation of the two fields a reviewer might read as inconsistent:**

- **The `calver:` field is the RUN timestamp, not the project version.** `calver: 2026.266.1124` is the run's artifact CalVer (`YYYY.DDD.HHMM`, UTC) — the bed runner names the `.check/<bed>/<calver>/` directory and tags its fixture images with `ComputeCalVer()` = "what time is it now". The plugin source is explicit that this is a time stamp, not a version identity:

  ```
  // candy/plugin-check/calver.go
  // ...tag their artifacts (image build tags, check-run dirs, ...) with
  // "what time is it NOW" in the canonical fixed-width CalVer form.
  // This is "what time is it now" (used to TAG an artifact created at this
  // moment) — NEVER the identity of the charly binary.
  func ComputeCalVer() string { return ComputeCalVerAt(time.Now().UTC()) }
  ```

  The run above executed at 2026-09-23 11:24 UTC (day-of-year 266), which is exactly what `2026.266.1124` encodes. `charly.yml`'s `version: 2026.249.2125` is the SCHEMA version (per `/charly-build:migrate`: "`version:` is the SCHEMA version … decoupled from the tag"), and the dev binary is `charly version 2026.249.2125`. These are three different axes by construction; the run `calver` is expected to differ from both.

- **The `charly box validate` counts are vocabulary-global plus this repo's one deploy.** `checked 1 deploy, 7 distros, 7 builders` reconciles directly: `1 deploy` is this repo's bed (`check-fedora-repo`, the sole deploy target the diff adds). `7 distros` + `7 builders` are the distro/builder definitions `validate` always checks, independent of the project — the same command in a directory with no `charly.yml` prints the identical distro/builder counts with no deploy count:

  ```
  $ cd /tmp && charly box validate
  charly box validate: OK — checked 7 distros, 7 builders; 0 warnings, 0 errors

  $ cd <clone> && charly box validate
  charly box validate: OK — checked 1 deploy, 7 distros, 7 builders; 0 warnings, 0 errors
  ```

  So the two counts above the project's own deploy are not authored in this file and are not expected to match the diff's box count.
